# Этап 5: наблюдатель Module 3 и граница с видеопотоком

21 октября 2026 года. Подготовлен локальный код для первого ограниченного
опыта Picamera2. Реальная камера не запускалась, новые файлы на Pi не
передавались. Проверки выполнены на Windows с имитацией камеры.

## Уточнение происхождения данных и цели

Пользователь уточнил: два CVAT-набора сняты обычным видеорегистратором,
предположительно фотографировавшим раз в 5 секунд. Это ориентир условий и
места установки, а не данные Camera Module 3 / Raspberry Pi 5. Равенство
камер, объектива, crop, ISP, выдержки или скорости не предполагается.
Интервал примерно 5 секунд сообщён пользователем и не является измеренной
каденцией сенсора. Между такими JPEG нет материала для проверки непрерывной
реакции экспозиции или пропусков видеопотока.

Цель аппаратной системы — собственный источник непрерывного потокового видео
с управляемыми настройками изображения. Конечная зона остаётся прежней:
примерно 1,5 м над асфальтом, до 4,5 м от передней части машины и около двух
полос. Для Module 3 нужны собственные измерения геометрии и качества.

## Что реализовано

- `code/road_observer_v01.py`: адаптация YUV420 и метаданных, ShadowAdvisor,
  ограниченная запись в новый каталог.
- `code/road_pi_observe_v01.py`: подготовка потоков main/lores, выборка
  согласованных кадров и метаданных, рекомендации без отправки, до 3 JPEG.
- `configs/pi_observer_lab_v01.json`: явная лабораторная конфигурация.
- `tests/test_observer_v01.py`: 14 офлайн-тестов.
- README и этот отчёт: запуск и практические ограничения.

Предыдущие ядро, адаптеры и опыты сохранены. Новые зависимости не устанавливались.

## Наблюдение без фиктивного управления

ShadowAdvisor сохраняет скоростной гистерезис, монотонное время и историю
подтверждения статусов. Предлагаемая команда удаляется из состояния как
**неотправленная**. В журнале она присутствует только как `would_request`;
`command_dispatched=false`, исполняемая команда и ожидание применения пусты.
Нет вызова `mark_sent` и выдуманного `COMMAND_OBSERVED`. Повторные рекомендации
рассчитываются от фактических параметров камеры, не от предыдущего пожелания.

Для этого используется небольшой внутренний подкласс versioned v0.2,
связанный с её защищёнными полями ожидающей команды. Эта зависимость явно
зафиксирована и покрыта тестами; при изменении ядра её нужно пересмотреть.
Камерный адаптер к этим полям не обращается.

В коде наблюдателя нет `set_controls`, вызова переключения sensor HDR или
сетевого сервиса. При будущем реальном запуске он всё же **конфигурирует и
запускает камеру**: выбирает размеры/форматы, sensor mode, запрашивает FrameRate
30 и применяет штатные defaults create_video_configuration. Это не пассивное
подключение к уже работающему чужому видеопотоку. Режимы AE/AF явно не
переопределяются; их фактические состояния и фокус записываются, а не считаются
заранее известными. Sensor HDR явно не задаётся и остаётся непроверенным.

## Данные и ограничения

Запрашиваются main 1920×1080 YUV420, lores 320×180 YUV420, sensor 2304×1296
10 bit, identity. Фактические размеры, формат, режим сенсора и transform
проверяются перед start. Проверяется идентификатор IMX708; он не различает
Standard/Wide и не заменяет проверку объектива/обзора.

Три зоны — новая лабораторная сетка внутри прямоугольника изображения,
не копия полигонов регистратора и не дорожная область в метрах. Загрузка
конфига с признаком чужого ROI отклоняется. Признак калибровки всегда false.

Фактические width/height/stride берутся из настроенной lores-конфигурации.
Несоответствующий YUV-массив не переинтерпретируется молча. Из одного request
берутся Y и метаданные; JPEG при выбранных моментах также относится к нему.
Request освобождается в finally, камера закрывается даже при ошибках.

По документированной семантике Picamera2 начало экспозиции первого пикселя
оценивается как `SensorTimestamp - ExposureTime * 1000` в наносекундах.
Сырые значения сохраняются, проверяются возраст/порядок/будущее время;
искусственный сдвиг часов не подбирается. На оборудовании это ещё предстоит
проверить. Использование timestamp как ID не превращает его в последовательный
номер кадра. [Руководство Picamera2](https://datasheets.raspberrypi.com/camera/picamera2-manual.pdf).

Сохраняются requested/actual configuration, исходный конфиг опыта, пределы
controls, версии пакетов, хеши трёх скриптов, фактические экспозиция/усиления,
длительность кадра, фокус, AE/AF, crop, доступность полей, время захвата и
анализа, место и проверки питания/температуры. Системные показатели обновляются
примерно раз в 5 секунд; это не непрерывный контроль питания.

Числа цели яркости, профилей, скорости и ROI — лабораторные, не дорожные.
Скорость 8 км/ч явно помечена SIMULATED. Допуски readback пока нулевые:
квантование не откалибровано, поэтому статусы достижения пределов могут
не сработать при близком, но не равном запросу фактическом значении. Это
ограничение записывается, а не используется для включения активного управления.

## Бюджет первого предлагаемого опыта

Петля наблюдения — до 15 секунд, не чаще одного выбранного кадра за 0,5 с,
не больше 30 наблюдений. На захват одного request задан тайм-аут 2 секунды.
Разрешены до трёх JPEG по 3 МБ, суммарно до 20 МБ всех выходных данных;
перед каждой записью проверяется сохранение 1 ГБ свободного места. При
ошибке остаётся частичный новый эксперимент; повторно использовать каталог
нельзя. Summary может не сохраниться при исчерпании места/бюджета, об этом
сообщается в stderr. Ошибки stop/close отражаются отдельно.

Настройка/старт/закрытие и системная диагностика добавляют время за пределами
15-секундной петли. Полной гарантии остановки при зависании драйвера эти
Python-ограничения не дают; первый запуск нужно наблюдать и ограничивать
снаружи. Освобождение поздно завершившегося асинхронного job и остановка
реального драйвера на этом этапе не проверены.

## Реально выполненные проверки

В Windows PowerShell, из корня проекта:

```powershell
python -B code/road_pi_observe_v01.py
python -B -m unittest discover -s tests -p 'test_observer_v01.py' -v
python -B -m unittest discover -s tests -p 'test_*.py' -v
```

Первая команда — dry-run: `dry_run=true`, `camera_started=false`, без импорта
Picamera2 и без файлов. Получены 14/14 новых тестов; общий набор — 62 проверки:
58 успешных и 4 ожидаемых падения исторической v0.1. Проверены согласованный
захват на FakeCamera, padding, единицы времени, границы ресурсов, default
dry-run, запрет существующего каталога, отсутствие отправки команд, отсутствие
тайм-аута неотправленных пожеланий, сохранение mode dwell и закрытие при ошибках
request/snapshot/stop. Это не результаты запуска на Pi.

Релевантные методы установленного Picamera2 0.3.37 прочитаны через SSH без
импорта/запуска камеры; проверены capture_request(wait=False), wait(timeout),
make_array и save в BytesIO. Остальные сведения основаны на документации и
офлайн-тестах. Успешный импорт/захват/JPEG на реальном устройстве ещё не доказаны.

## Следующий аппаратный шаг — после отдельного согласования

Предлагается скопировать только три файла code (core v0.2, observer helpers,
Picamera2 observer) и один JSON-конфиг в **новый** корень эксперимента. Старые
исходники не заменяются; перед копированием снова проверить место и питание.
Первый запуск — описанный 15-секундный опыт с результатами в новом подкаталоге.

Пример команды **на Raspberry Pi**, из нового корня после согласованного
копирования; `run_001` должен отсутствовать:

```bash
python3 -B code/road_pi_observe_v01.py --run-camera --allow-uncalibrated-lab --output run_001
```

Ожидаются setup.json, observations.jsonl, до трёх JPEG и summary.json.
Критерии: реальный readback/stride/времена валидны, ноль команд политики,
приемлемая нагрузка/питание, бюджет соблюдён, камера освобождена. Результаты
просмотреть локально; успешность заранее не обещается. Эта команда пока
не выполнялась и разрешением на запуск не является.

## Переход к собственному видеорегистратору

Предлагаемая цепочка: sensor/ISP → main-поток → кодирование → ограниченная
очередь передачи → приёмник. Параллельно lores того же сенсора даёт статистику
для управления экспозицией. Наблюдатель выше проверяет подготовку кадров и
метаданных, но не реализует кодирование/доставку видео.

Следующие отдельные измерения: короткий ограниченный тест кодирования в sink
без больших видеодампов; затем передача на выбранный получатель. Сравнивать
MJPEG/H.264 по CPU, битрейту, задержке, пропускам и сохранности мелких деталей.
На Pi 5 кодирование H.264/MJPEG в описанных Picamera2 энкодерах программное,
поэтому доступность 1080p30 нельзя выводить из сенсорной каденции.
[Описание энкодеров](https://datasheets.raspberrypi.com/camera/picamera2-manual.pdf).
Протокол и сетевое открытие выбираются после уточнения получателя и канала.
