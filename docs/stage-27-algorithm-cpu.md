# CPU, потоки и кодеки расчёта без веба

26 октября 2026. На той же Raspberry Pi выполнены два изолированных replay
benchmark: TargetTracker + ShutterPolicy, сохранённые реальные crops,
загруженные в память до измеряемого участка. Камера не открывалась,
HTTP, JPEG encoding/decoding и видеокодеки отсутствовали. Live не останавливался.
Pi имеет четыре CPU cores. Это стоимость вычислительного компонента,
не всего capture/ISP тракта без веба.

## Измерения

Непрерывный прогон: 505 оценок, wall 7.8503 с, process CPU 7.8492 с,
то есть 1.00 core-equivalent при работе без пауз. Один OS thread;
загружены системные libblas/liblapack, многопоточный runtime не наблюдался.
threadpoolctl отсутствует, не устанавливался. Время оценки: среднее
15.54 мс, медиана 15.24, p95 21.33, максимум 23.71 мс. Это распределение
конкретной записанной карточки, а не WCET для любой сцены.

В отдельном pacing прогоне: 84 оценки с периодом .12 с, wall 10.0801 с,
process CPU 1.6526 с. Реально измерено 16.40% одного ядра, то есть
4.10% суммарной мощности четырёх ядер при таком пересчёте. По непрерывному
прогону расчётная оценка была 12.95%; отличие может отражать governor,
кэш, состояние CPU, фоновые процессы и startup. Для короткого ответа
используется измеренный paced результат около 16%, а не только экстраполяция.
При работе без пауз поток занимает ядро; выделять отдельное ядро
на периодические вызовы с этой частотой не требуется по данному опыту.

В живом коде оценка вызывается не чаще раза в .12 с (до 8.33 Гц),
не на каждом из 30 входных кадров. Это намеренное разделение частоты
захвата и управления. Экстраполяция непрерывного прогона на 30 оценок/с
даёт около 47% одного ядра, но такой аппаратный поток не проверен.

RAM прогона с заранее загруженными 101 изображением около 46 МиБ;
это включает приблизительно 18 МиБ replay dataset. Не противоречит
предыдущему измерению потокового изолированного процесса 28–29 МиБ
с добавкой алгоритма/данных/буферов 5–6 МиБ поверх Python/NumPy.
Память этого benchmark нельзя выдавать за чистую память ядра.

## Кодеки и ускорители

Сам tracker/policy не создаёт ни видеодекодер, ни видеоэнкодер: ноль.
В этой CSI схеме Picamera2/libcamera предоставляет main YUV420 после
аппаратного ISP; входящего H.264/H.265 потока, требующего декодирования, нет.
Расчёт читает Y и выдаёт controls. GPU/NPU/нейросетевой inference алгоритм
не использует. Драйверы/ISP и получение/копирование кадров — отдельный слой.
Цветной веб-preview кодирует YUV crop в JPEG через simplejpeg; это
расход демонстрации, не требование алгоритма. Передача видео потребителю
в будущем может потребовать отдельного кодирования независимо от policy.

Первый вариант измерительного скрипта не завершился из-за ненужного
несовместимого NumPy import после расчёта; численные результаты этого
варианта не использованы. Повторные benchmark завершились успешно.
Результаты в игнорируемом runs/colour_preview_20261026_001:
cpu_algorithm_replay_002.json, cpu_algorithm_paced_001.json.
Новых пакетов/исходников на Pi не записывалось. Код не менялся, тесты
не повторялись; последний набор — 117 тестов предыдущего этапа.
